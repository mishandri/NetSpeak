# Сборка под Linux

Ветка заведена под Linux. Рабочего бинарника под Linux пока нет — здесь
лежит заготовка сборки и разбор того, что мешает.

Коротко: собрать здесь нечем, но и не нужно. Сборка уезжает на серверы
GitHub по тегу, и для этого не требуется ни Linux на этой машине, ни
Docker, ни WSL. Нужен один файл и одно действие в настройках репозитория.

---

## Как это будет работать

1. Вы кладёте файл `.github/workflows/release-linux.yml` в репозиторий
   (он уже в этой ветке).
2. В репозитории включаете Actions: **Settings → Actions → General →
   «Allow all actions and reusable workflows»**.
3. Пушите тег `client-v1.0.4` или `server-v1.0.4`.
4. GitHub сам собирает оба бинарника и кладёт их в релиз этого тега.
   Рядом с `.exe` появятся файлы без расширения — их и качают на Linux.

Ручной запуск: **Actions → Сборка Linux → Run workflow**. Так удобно
проверить, что сборка жива, не выпуская релиз.

Если Actions в репозитории не включается или не запускается — напишите
мне, посмотрю, что именно он пишет (вкладка того самого запуска).

---

## Чего не хватает для сборки здесь, на этой машине

| Чего | Есть ли | Что это значит |
|---|---|---|
| Linux (WSL) | нет, не установлен | PyInstaller не умеет собирать Linux из Windows |
| Docker / Podman | нет | второй способ запустить Linux, тоже отсутствует |
| Виртуализация в системе | **есть** | единственное, чего для WSL и не хватает |
| Права администратора | не проверял | без них WSL не поставить |
| `gh` (GitHub CLI) | нет | не нужен: файлы в репозиторий попадают через `git push` |

Виртуализация включена, система — Windows 11 Pro. То есть WSL поставить
можно: нужны права администратора и одна перезагрузка. Дальше
`wsl --install -d Ubuntu`.

**Но ставить WSL ради этого не стоит.** Он занимает место, требует
перезагрузку и ещё одной сущности, которую надо потом обновлять. Сборка
на серверах GitHub делает то же самое, не трогая вашу машину, и к тому же
проверяет сборку на чистой системе — а это как раз то, чего не бывает на
рабочем компьютере.

Понадобится WSL только если захочется **запускать** собранное под Linux
для проверки: убедиться глазами, что окно появляется, микрофон работает и
сервер виден в сети.

## Что мешает коду работать под Linux

Это не «не хватает», это нужно доделать руками. Список по убыванию
сложности.

### 1. Значок и версия в файле — только для Windows

`src/netspeak.spec` просит у PyInstaller `.ico` и файл с версией.
Под Linux значок другой (PNG), а ресурса «версия в свойствах файла» там
нет вообще.

*Что делать:* завести `netspeak-linux.spec` и `build_linux.py`, которые
собирают без `icon=` и без `version=`. Дальше версия видна только в
настройках приложения — это уже и так есть.

### 2. Брандмауэр — целиком про Windows

`src/netspeak/firewall.py` вызывает `netsh advfirewall`. Под Linux его
нет; там `ufw` или `iptables`, и права нужны не такие.

*Что делать:* на Linux кнопка «Разрешить в брандмауэре» прячется, а при
первом запуске пишется честное предупреждение, что входящие соединения
могут блокироваться и что делать. Полноценной поддержки `ufw` я бы не
делал: она требует `sudo` из окна, а это отдельный разговор про права.

### 3. Адреса сети — команда Windows

`src/netspeak/netinfo.py` спрашивает `ipconfig`. Под Linux это
`ip -4 addr` или `hostname -I`.

*Что делать:* ветка на выбор команды. Это самое мелкое.

### 4. Номер компьютера — реестр Windows

`src/netspeak/device.py` берёт `MachineGuid` из реестра, чтобы номер
человека переживал перенос папки на другой компьютер.

*Что делать:* на Linux — `/etc/machine-id`. Он же системный и уникальный,
так что смысл сохраняется. Это тоже мелкая правка.

### 5. Значок в трее и запуск сервера

`window_keeper.py` работает с `.ico` и Win32-иконкой. `serverctl.py`
запускает `NetSpeakServer.exe`.

*Что делать:* значок поменять на PNG, запуск — на `sys.executable`.
Трей на Linux стоит делать только если пойдёт `libayatana-appindicator3`
(он в списке пакетов уже есть). Без него программа просто работает без
значка в трее — и это допустимо, потому что окно на виду.

### 6. Обновление — файлы другие

`src/netspeak/updater.py` качает `.exe` и меняет исполняемый файл. Под
Linux собирать надо `.tar.gz` с бинарником, и «новый файл» там просто
новый файл в распакованной папке, без подмены на месте.

*Что делать:* это самая объёмная часть. Общий код уже есть, но формат
другой, и тесты обновления придётся переписать под него.

### 7. pywebview под Linux — отдельная история

Окно рисует GTK через WebKit2GTK. Пакеты уже перечислены в файле сборки.
Но: WebView2 на Windows и WebKit2 на Linux — разные движки, и поведение
мож��ть отличаться. Особенно это касается микрофона и работы с
разрешениями — а это самое важное в программе.

*Что делать:* после первой сборки обязательно проверить руками в Linux:
микрофон, звук, «Проверить связь», сохранение имени с аватаром. Автотесты
здесь бессильны — они и на Windows не могут проверить звук.

## Что уже сделано

- Ветка `linux` в репозитории.
- `.github/workflows/release-linux.yml` — сборка по тегу на `ubuntu-22.04`
  с нужными системными пакетами и приложением файлов к релизу.
- `requirements-linux.txt` — зависимости с закреплёнными версиями.

## Чего нет

- `build_linux.py` и `netspeak-linux.spec` — их надо написать, это первый
  шаг, и он делается на этой машине (Python у нас есть).
- Правки пунктов 2–6 в коде.
- Ни одного собранного и ни разу запущенного бинарника под Linux.

## С чего начать, когда дойдёт дело

1. Написать `build_linux.py` и `netspeak-linux.spec` — собирается
   настоящий файл, и сразу видно, чего код не хватает.
2. Запустить первую сборку по Actions, посмотреть, что она скажет.
3. По одному закрывать пункты 3 и 4 — они самые мелкие.
4. Собрать, запустить в WSL, проверить руками всё, что в пункте 7.
5. Остальное (брандмауэр, трей, обновление) — по желанию.
